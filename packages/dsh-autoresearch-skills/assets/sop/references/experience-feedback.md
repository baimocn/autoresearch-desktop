# 经验回流提示词（可直接复制给任意题目会话）

> 用途：让**每个题目/项目的会话**把它在本次任务中积累的可复用经验，回流到统一的 SOP 仓库。
> 本文件本身也是一份**待回流的产物** —— 若你在读它的仓库里，说明流程已经跑通一次。

## 一、最短可用版（复制以下整段即可）

```
把你在本次任务中积累的可复用经验，回流到 SOP 仓库。

仓库：baimocn/autoresearch-sop（默认分支 master；本机 git push 对
github.com:443 不通，必须用仓库自带的 tools/push_via_api.py 走 API 提交）

要求：
1. 只写**可复用的判断与操作**，不写本次任务的具体数据、主机地址、凭据、
   或任何私有材料（分数、模型、数据集明细都不进仓库）。
2. 每条经验必须包含：**症状/错误原文 → 根因 → 修法（可复制粘贴的命令或步骤）**。
   只写"要小心 XXX"不算经验。
3. 用真实数字（耗时、字节数、错误码、次数），不写"大约""很多"。
4. 与仓库既有内容对照，**不重复造轮子**：
   - 已有同主题条目 → 追加/修订那一条，不要新建重复条目
   - 属于新主题 → 新建，并保持编号连续、风格一致
5. 改完必须做三件事：
   a) 跑仓库自检：`python scripts/validate_skills.py`
   b) 提交信息里写清"哪条经验对应哪次事故"
   c) 提交后用 `--verify` 逐文件核对远端大小
6. 提交前先 `--dry-run` 看一眼将写入哪些文件。

产出：一次提交 + 一段说明"改了哪些文件、每条对应什么事故、验证结果"。
如果本次没有**可复用**的经验（只有一次性操作），如实说"无回流"，不要硬凑。
```

## 二、完整版（含判定标准与边界，推荐团队统一使用）

```
## 任务：经验回流到 SOP 仓库

你在本次任务中可能踩过坑、绕过弯、发现过反直觉的事实。
其中一部分对**其他题目**同样有价值——把它们抽象出来，回流到统一仓库。

### 仓库与通道

- 仓库：`baimocn/autoresearch-sop`
- 默认分支：`master`
- **必须用 `tools/push_via_api.py` 提交**：本机 `git push` 对
  `github.com:443` 不通（`Connection was reset` / `Could not connect`）。
  该工具走 `api.github.com` 的 Git Data API，只依赖已登录的 `gh` CLI，
  不接触任何凭据。
- 提交前先自检：`python tools/push_via_api.py --repo <owner/name> --branch master --selftest`

### 什么该回流（判定标准）

**该回流** —— 满足全部三条：
1. **可复用**：其他题目/其他会话遇到同类情形时会需要它
2. **可执行**：能写成命令、步骤、判据或检查清单
3. **非显然**：不是常识，而是"不看就一定会踩"的那种

**不该回流**：
- 一次性操作（某次特定的路径、某次特定的参数）
- 常识性内容（"记得保存文件"）
- 只对本题成立的结论（某题的具体分数、超参、数据分布）
- 任何私有材料：凭据、token、内网地址、私有数据/标签/模型明细

**边界测试**：假设换一道完全不同的题，这条经验还有效吗？
有效 → 回流；无效 → 留在本题的本地记录里。

### 写入位置

| 经验类型 | 写入文件 | 写法 |
|---|---|---|
| 可执行判据 / 流程步骤 | `SKILL.md` 的执行规则（编号续排） | 一句话规则 + 指向详情 |
| 踩坑实录 / 反直觉事实 | `references/field-lessons.md`（编号续排 Lxx） | 症状→根因→修法，带真实数字 |
| 跨题统计规律 / 死因 | `references/failure-patterns.md` | 表格一行：判据 / 可执行判法 / 实测案例 |
| 分阶段操作细节 | `references/production-sop.md` 对应 V 段落 | 在既有段落内追加"补充"子节 |
| 可执行门禁 | `tools/<name>.py` | 只读、三态退出码、有 `--help` |

### 硬性要求

1. **症状必须要真实原文**：报错信息照抄，不要转述。
   （例：`invoking the NVIDIA Container Runtime Hook directly is not supported`）
2. **必须有根因**：只写症状和修法、不写根因，下次换个表象就认不出来。
3. **修法必须可复制**：给出命令或步骤，不要写"按文档配置一下"。
4. **用真实数字**：耗时精确到秒/分钟、字节数、次数、退出码。
   禁止"大约""很多次""比较慢"。
5. **不重复**：先通读仓库既有条目。同主题就**修订原条目**，
   不要新建平行条目（避免同一事实多个真源——这正是仓库 L14 要防的）。
6. **编号连续**：规则编号、L 编号都必须接续，不跳号、不复用。

### 必做验证（缺一不可）

```bash
# 1) 仓库自检（结构 / 脱敏 / 本机路径）
python scripts/validate_skills.py

# 2) 演练：看清将写入哪些文件
python tools/push_via_api.py --repo baimocn/autoresearch-sop --branch master \
    --dry-run --message-file /tmp/msg.txt <改动文件...>

# 3) 真实提交 + 逐文件核对远端大小
python tools/push_via_api.py --repo baimocn/autoresearch-sop --branch master \
    --message-file /tmp/msg.txt --verify <改动文件...>
```

**不要只看命令的退出码** —— 必须回读"远端 HEAD 的 commit message"
与"逐文件大小对比"两处输出，确认内容真的上去了。

### 新增工具的要求（若本次沉淀了可执行门禁）

- **只读**：不得修改被检查对象
- **三态退出码**：`0`=通过 / `1`=硬失败 / `2`=需人工确认
- **有 `--help`**，且在 docstring 里写明"来源：哪次事故"
- **必须真实跑过一次**（在真实或可丢弃环境），把实测输出贴进提交说明
- 不接触凭据、不写绝对路径

### 产出格式

提交完成后，用一段话报告：

```
改了哪些文件：
  <路径> —— <这条对应什么事故/教训>

新增/修订的条目编号：规则 x–y；Lxx–Lyy；工具 <name>.py
验证结果：
  validate_skills.py = 通过/不通过
  远端 HEAD = <sha 前 8 位> | <提交信息首行>
  逐文件核对 = N/N 一致
未回流的内容及原因：<如实列出，没有就写"无">
```

### 诚实性要求

- 没有可复用经验时，**如实说"本次无可回流内容"**，不要为凑数写空话。
- 经验写得不准比不写更糟 —— 它会被其他会话当成事实照做。
- 若某条经验你只有一次观察、不确定是否普适，**在条目里标注"单次观察，待复验"**。

## 四、可以同时发给多个会话吗？

**可以，但必须遵守三条纪律**，否则会**静默丢数据**（不报错，内容却没了）。

### 为什么危险

提交流程是 `读 head → 建树 → 提交 → 更新引用`，这是典型的 read-modify-write。
两个会话同时跑时，双方可能读到**同一个 head**，各自基于同一个 `base_tree` 建树：

```
会话A: 读 head=H ──> 建树(含A) ──> 提交CA ──> 引用指向CA     ✓
会话B:      读 head=H ────────────> 建树(含B,不含A) ──> 提交CB ──> 引用指向CB
                                                                  ↑
                                          结果：A 的改动被 B 的树整体回退
```

从提交图上看是"B 接在 A 后面"，但 **B 的树里没有 A 的文件**——A 的改动消失了。

### 三条纪律

| # | 纪律 | 原因 |
|---|---|---|
| 1 | **用 CAS 版本的工具**（本仓库的 `push_via_api.py` 已内置 compare-and-swap 重试） | 引用更新失败会自动重新读取 head 与 base_tree 再试，不同文件的改动不会互相覆盖 |
| 2 | **各会话改不同文件 / 不同段落** | CAS 只能保证"不同文件不丢"。两个会话若都往 `field-lessons.md` 追加"下一条 Lxx"，后提交者仍会覆盖前者——这是**语义冲突**，工具层面无解 |
| 3 | **提交后回读查重** | 用 `--show <path>` 拉最新内容，确认自己的条目在、且编号没和别人撞 |

### 推荐做法：让各会话写独立文件

最稳的方式是**一个会话一个文件**，避免共享文件的追加冲突：

```
references/cases/<题号或日期>-<主题>.md      ← 各会话各写各的
```

若确实要追加到共享文件（如 `field-lessons.md`），按此顺序：

```bash
# 1) 先拉最新，看当前最大编号
python tools/push_via_api.py --repo baimocn/autoresearch-sop --branch master     --show references/field-lessons.md | grep -E "^## L[0-9]+" | tail -5

# 2) 基于最新编号写自己的条目（不要凭记忆写编号）

# 3) 提交（CAS 自动处理并发；失败会自动重试）
python tools/push_via_api.py ... --verify <文件>

# 4) 回读，确认自己的条目在、编号没撞
python tools/push_via_api.py ... --show references/field-lessons.md | grep -E "^## L[0-9]+" | tail -5
```

### 并发能力边界（如实说明）

| 场景 | 是否安全 |
|---|---|
| 两个会话推**完全不同的文件** | 安全（CAS 保证） |
| 两个会话推**同一文件的不同段落** | 大概率安全，但需回读确认 |
| 两个会话追加**同一文件的同一位置**（如都续写 L17） | **不安全** —— 后写者覆盖前者，必须靠人工定编号 + 回读查重 |
| 两个会话**同一秒**提交 | 安全 —— 后者引用更新失败后自动重试 |

### 提升并发成功率的做法

- 把 `--retries` 调大（默认 5；并发会话多时用 10）
- 各会话**不要同时提交**：可在提示词里约定错开（如按题号奇偶分批）
- 提交信息里带上**会话/题目标识**（如 `[auto2768]`），便于冲突时定位

## 三、自举验证记录（本文件如何被推送）

本文件与 `tools/push_via_api.py` 是**同一批产物**，且用后者推送到远端：

1. `tools/push_via_api.py --selftest` → gh 已登录 + 仓库可达
2. `--dry-run` → 确认将写入的文件清单
3. 正式提交 + `--verify` → 逐文件大小一致

这构成一次**自举**：工具把它自己和它自己的使用说明推了上去。
若你在远端读到本文件，说明这条通道是可用的。

并发安全（CAS，compare-and-swap 重试）经**真实并发实测**：
同时启动两个进程推不同文件，验证两者均落地、无静默回退。
测试方法见下方"验证 CAS 是否生效"。


### 验证 CAS 是否生效（可自行复现）

```bash
# 制造并发：两进程同时推不同文件
python tools/push_via_api.py --repo <owner/name> --branch master     --message "concurrent A" --verify <fileA> &
python tools/push_via_api.py --repo <owner/name> --branch master     --message "concurrent B" --verify <fileB> &
wait
# 期望：两个文件都在远端；若某个进程输出"引用已被他人前移，重新读取基线"，
#       说明 CAS 生效并自动重试成功。
```

**注意**：若两个进程恰好完全错开（未撞上），本次不会触发重试，这不代表 CAS 无效。
要强制触发，可用 `--assume-head <过期的 SHA>` 复现冲突路径。
