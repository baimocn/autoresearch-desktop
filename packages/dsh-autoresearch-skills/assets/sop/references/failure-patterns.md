# 跨题目失败模式（2026-10-07 全项目只读提炼）

> 来源：项目内 9 条题线 + 错误登记册（E01–E83，83 条真实事故）+ 选题筛选报告 + 归因报告的**只读提炼**。
> 价值：单题教训是轶事，**跨题统计才是规律**。本文件把规律固化成可执行判据。

## 一、宏观结论（项目原话，照抄）

> **「本项目 14 道题 7% 成功率，死因 100% 在选题。」**
> **「官方三项（来源/难度/重复）只管入场券，管不到「题目能不能做出来」。」**

**推导**：选题阶段（P0/P1）是整个流程**唯一的高杠杆点**——93% 的题死在这里，而这一阶段的检查**几乎全是零成本的静态判据**。

## 二、★★★ 选题期死因过滤器（动手前必过，全部零成本）

来自项目实战总结的六类死因 + 玩具论文判据。**任一条不过 = 弃题，不进 P1。**

| # | 死因 | 可执行判法（不是"要小心"） | 实测案例 |
|---|---|---|---|
| 1 | 官方仓不存在/空壳 | GitHub API 查仓（`size`/`pushed_at`/contents）；**PMLR 论文必须抓 PMLR 页面 HTML**（PDF 里常无代码链接） | auto2027/1931 无 repo 弃；auto1891 repo 仅 537B README 暂弃 |
| 2 | 有权重 ≠ 有训练代码 | `git clone --depth 1 --filter=blob:none --no-checkout` 取文件树 → grep `def main\|Trainer(`；**HF 只有 safetensors = 只是训练产物** | 通用判据 |
| 3 | **baseline 口径不可比** | 论文报的 baseline 明显低于社区公认值时，先查「**这个 baseline 是不是作者自己跑的**」 | **auto1851**：论文 58.0 vs 社区 81.8，差 23.8 → 增益 +34 的前提是被低估的 baseline |
| 4 | 判据被混淆变量污染 | 对比两侧数据前必查六项：**大小 / 行数 / 长度分布 / source / id 重叠 / md5** | auto1352：长度差 8.7 倍、dsir 维与长度 rho≈−0.96 |
| 5 | **基线被更笨的方法反超** | 先跑 persistence / 最近邻这类 **trivial 基线** | **auto1430**：persistence(2.40) 打败论文方法(2.69) 与基线(6.36) |
| 6 | 广度不足 | 主表所有格子必须 **≥3 个不同 benchmark/数据集** | 体检 61 道 REJECT_不严谨 |

**玩具论文四判据**（缺一即降权）：
① 只在 1–2 个 benchmark 验证；② baseline 自实现（=1851 死因）；③ 不报 ±σ（**3σ 判据没有分母**）；④ 无消融。

**注意**：方法与"简单/年代久"本身不是失败依据——排除的是**不严谨**，不是简单。

## 三、★★ 2001 同构标准（选题画像）

**要**：经典 ML / GB 级小数据集 / 训练型任务 / 官方代码完整 / **增益幅度大（论文 Δ≥10%，而非 +7%）** / 指标为**物理量**（reward、成功率、时间、仿真回报）。
**回避**：LLM 推理优化类（增益小、要论文级算力才显形）；LLM-judge / 人工评测 / win-rate（**U 无法零泄漏构造**，且官方严禁反推 U）。

## 五、★★★ 决策类错误（最难防，本仓库的核心关注）

| E33/E61 | 把 7h 当通用折扣 | 7h 例外需全部例外证据齐备 |
| E18/E19 | 选择性挑数、选择性披露 | 保留全部结果，不挑不裁 |

**共性**：以"印象/直觉"替代一手证据；以"改参数变绿"替代"改设计 + 上报"。

## 五点五、★★★ 环境与交付类死因（2026-10-08 新增，来自 auto2768）

前五节聚焦"选题错"，本节补的是**选题对了但交付链断**这一类——它们不烧 GPU 钱，
但会让**已经做完的题**卡在 H06/QA17，等于白做。全部零成本或低成本可查。

| # | 死因 | 可执行判法 | 实测案例 |
|---|---|---|---|
| 7 | **NOP 是"模拟"而非原生 Trial** | 核对同一 Trial 的 config/result/reward/日志是否**同源**；`agent_info.name == "nop"`；`verifier_environment_mode == "separate"`。手工 Docker 模拟 + 事后补字段不构成原生 Trial | **auto2768**：包内 `validation/nop` 被平台判为"含主动训练和手工移交，不能证明原生 Harbor NOP" |
| 8 | **环境前提未预检就开跑** | 跑前实测五项：GPU 直通 / nvidia runtime 注册 / buildx / compose v2 / 宿主容量 vs 题面声明 | auto2768 连撞 6 类（`nvidia-container` hook、只读命名空间、`unknown flag: --file`、`Range of CPUs`、`timed out after 1800`、`early EOF`） |
| 9 | **运行绑定未与交付字节交叉验证** | 运行前算题包全量 SHA-256 清单，交付时逐文件比对；不能只凭"我跑过" | auto2768：平台指出"最佳方法所报 train.py 哈希与交付文件不一致" |
| 10 | **同一事实多套声明（双真源）** | 对锚点/口径/基线做全包扫描：同名量只能有**一套生效值**；变更必须披露并说明时间线 | auto2768：`calibration.json` 写 U=75.1333，另有三处写 U=100.0，且自带 `no_post_result_upper_bound_tuning: true` 与之冲突 |
| 11 | **交付表/报告与实际包脱钩** | 表里每个数字都要能指回包内文件；交付包名必须指向**实际最新**的那个 zip | auto2768：出题表格"参考解分数"列写的是**已被判无效的旧 v7 泄漏协议**数值（70.5667/8.6833/5.43σ） |
| 12 | **质检报告字段契约未对齐** | 写 review.json 前先 `grep "raise ValueError"` 抓全字段约束，一次性对齐 | auto2768：同一份 review 撞 **21 次** `inspection_error`，`QA17.remediation` 单独撞 6 次 |
| 13 | **集成方法的提交物只存 1/N 成员** | 源码出现集成却只 `torch.save(models[0])`；用单模型复算集成的预测必然失配（**失配率 10%+ 而非全错**是典型指纹）。打包前静态 grep 拦截 | **AutoRe0823**：5 成员集成只落盘第 1 个，其余 4 个从未写盘 ⇒ 原提交无法逐样本复算；三组候选成员逐一实测，失配 2736 / 1130 / 1205（10000 张） |
| 16 | **task.toml 未过原生契约** | 用目标版本 `TaskConfig` 真加载；四项：`[task].name` / `network_mode` 枚举 / `environment_mode=separate` / `build_timeout_sec`。用 `tools/harbor_task_contract.py`（0/1/2） | **auto2001**：3 个 schema 错误 + 600s 默认超时（实测首建 1578s），原生 Harbor 根本起不来 |
| 17 | **改了被质检锚定的交付物后自查通过** | 对照交付物当前 SHA 与质检报告引用的 SHA；不一致即旧结论作废，须上报重检 | **auto2001**：质检 PASS 后改了 task.toml 三行并重报 PASS；另实测 156 文件中 23 个变化、仅 1 个登记 |
| 18 | **结构化表格用库回写** | 改后做全表逐单元格 diff：实际差异集必须**等于**意图修改集 | **auto2001**：openpyxl 回写把日期列降级为 `46299.6105208333`、列宽 19→13，并改坏同表其他题目行 |
| 14 | **同名文件误当同一版本** | 取回权重/源码后必须 `sha256sum` 与包内绑定字段对账；方法名（`method`）字段是最便宜的版本指纹 | **AutoRe0823**：中间副本 model.pt 11,154,050 B / Dev 83.48 与最终版 11,155,266 B / Dev 86.54 同名不同源，导致**连续两次错误结论并撤回** |
| 15 | **隔离面靠"环境变量模拟"自检 / 门禁匹配到注释** | 沙盒自检禁用 `PYTHONHOME` 模拟（`-I` 忽略所有 `PYTHON*`）；静态门禁只看**代码行**（排除注释），且必须用**故意破坏的副本**验证它会 FAIL | **AutoRe0823**：`-I`+`PYTHONHOME` 误报"根内含 torch"；clone3 的 ENOSYS 代码删掉后门禁仍报 PASS（匹配到注释字样） |
| 19 | **CRLF 仓库里 `git diff` 行数被放大 / 合并被永久拒绝** | 真实改动用 `git diff --ignore-cr-at-eol` 复核；合并被"local changes"拒绝而 `checkout`/`stash` 无效时，改用 API 工具提交（不读本地索引）；提交前核对远端 HEAD 与编号 | **本仓库自身（2026-10-09）**：`git merge --ff-only` 连拒 4 次；同一文件普通 diff 报 236 行、忽略行尾仅 14 行；`production-sop.md` 报 1644 行、实际 22 行 |

**共同特征**：这六类的**证据成本极低**（都是核对/预检/交叉验证），但**返工代价极高**
（要走平台受理周期）。⇒ 应全部**左移**到提交之前。

**可执行门禁**：`tools/nop_preflight.py`（死因 8）。其余五类按 L12–L16 的清单人工过。

## 九、给 AI 出题专家的执行清单（本仓库直接可用）

**P0（零成本，30 分钟）**：
1. 六类死因过滤器逐条过（§二）

**只有 5+8 都返回"可行"才申请正式预算。**
