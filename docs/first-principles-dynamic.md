## 零、为什么要重推

用户提出的命题是：

> 上游质检 skills 不会停在 0.3.4，SOP 也会有更多信息整合，全局应该是动态而非静止，
> 核心是**大模型能让全局活跃起来，但有一些约束是必须的**。

这个命题包含一个隐含的架构主张：**"静态"是问题，"动态"是答案**。
我必须先检验这个二分法本身对不对 —— 因为如果它错了，后面所有设计都会错。

## 一、撤回：我第二轮的建议是错的

### 我当时说了什么

`docs/upstream-integration-review.md` §六 建议：

> **立即**：把 `gates/lib/tools.js:145,155` 改为 `qa-0.3.4/…`，
> 与 `dsh-autoresearch-qa` 的口径对齐。
> **单一真源**：三份副本收敛为一份（真上游 0.3.4）。

### 为什么这是错的

我回查 `catalog.js:8` 与 `:22-25`，发现**优先级是刻意设计的**，不是疏忽：

```js
// catalog.js:8
 * 同一 name 出现在两份来源时，教程附件版本优先（教程正文以它为准），
 * 但候选来源全部保留，便于比对版本差异。
// catalog.js:22-25
export const SOURCES = Object.freeze([
  { id: 'tutorial-v3',    root: 'skills-0.3.2',            rank: 100, ... },
  { id: 'upstream-0.3.4', root: 'skills-upstream-0.3.4',   rank: 200, ... },
])
```

**两个来源服务两个不同目的**：
- `tutorial-v3`（0.3.2）= **权威口径**。教程正文规定了判据，专家签字的是这套。
- `upstream-0.3.4` = **上游最新实现**，供比对与参考。

我把"两个来源有不同职责"误读成了"没同步好的重复副本"。
按我原来的建议收敛成一份，会**删掉权威口径**，让判据漂移到上游 —— 那恰好是
SOP「同一事实单一真源」要防的反面：不是"只有一个文件"，而是"只有一个**生效**声明"。

### 但 §3.2 的发现依然成立

版本分歧**确实**造成了功能失效 —— 这是实测的，不撤回：

```
LIVE 0.3.2  → error: unrecognized arguments: --release-self-check --reviewer-provider …
UPSTREAM 0.3.4 → 参数全部被接受
```

**修正后的诊断**：问题不是"引用了旧版"，而是**引用关系与职责归属不一致**：

| 包 | 引用 | 是否与其职责一致 |
|---|---|---|
| `skills/lib/catalog.js` | 0.3.2 优先（权威口径） | ✅ 一致 —— 它负责"教专家按教程判" |
| `gates/lib/tools.js:145,155` | **硬编码 0.3.2** | ❌ **不一致** —— 它注册的是**发布门工具**，发布门要的是 0.3.4 能力 |
| `qa/index.js:83` | 0.3.4 优先 + fallback | ✅ 一致 —— 它负责"产出发布门证据" |

所以正确修法**不是"统一到 0.3.4"**，而是：**让引用跟随职责**。
`tools.js` 注册的是发布门工具，就该用 0.3.4——但**不是**把 `catalog.js` 的权威口径也改掉。

> **教训**：我上一轮把"消除重复"当成了目标。但重复本身不是缺陷，
> **未声明的重复**才是。三份副本的错在于没有一处声明"谁是权威、谁是参考、谁在何时生效"。

## 二、"静态 vs 动态"这个二分法本身是错的

### 反例：完全动态是灾难

如果"上游一变就自动跟进"，那么：
- 上游某次提交改了 `R_norm` 区间 → 已发布题目的判据漂移 → **旧结论失效且无人知晓**
- 上游引入一个 bug（如 D1 的端点颠倒）→ 自动同步 → **把缺陷引入本仓**
- 上游把某个判据改严 → 已在跑的题目突然全部不通过 → **训练中断**

`docs/upstream-defects.md` 已经记录了 D1 —— 一个**真实存在的上游缺陷**。
"自动同步上游"会把这个缺陷直接搬进来。

### 正确的二分不是 静态/动态，而是：

| 维度 | 应该静态（冻结） | 应该动态（可演进） |
|---|---|---|
| 判据本体 | 已发布题目的评分口径 | 新题采用的口径 |
| 上游代码 | 已锚定的证据 | 新运行的执行 |
| 依赖解析 | 已冻结的引用 | 引用**如何**解析 |

**核心洞察**：动态的不是"内容"，而是**"解析规则"与"变更的可见性"**。
内容是数据，规则才是机制。这正是"约束必须存在"的准确含义 ——
约束不是阻止变化，而是**让变化可追溯、可控、可回滚**。

## 三、真正的第一性问题

剥掉所有实现细节，问题的本质是：

> **一个交付物的结论，依赖于它当时所用上游工具的某个具体版本；
> 而那个版本会变。如何让"依赖了哪个版本"这件事，永远可回答？**

### 三层分解（每一层都可独立验证）

```
L1  记录   当前引用了什么？        → 来源清单（path → sha256 + upstream version）
L2  检测   它和上游还一致吗？      → 漂移检测（比对，不改动）
L3  决策   不一致时谁来改、怎么改？ → 模型 + 约束（在门禁允许的窗口内改）
```

**奥卡姆检验**：只做 L1+L2 就能把风险从"不可见"降到"可见"。
L3（自动改）收益小、风险大 —— 因为改错判据的代价远高于晚一轮发现漂移。

**所以最小正确方案是：L1 + L2 必做，L3 做成"建议"而非"自动执行"。**

## 四、约束的形式化（"有一些约束是必须的"）

用户说约束必须存在。那就必须把约束写成**可执行判定**，而不是文档里的劝告。
从已有代码里提炼，真正的约束有三条：

| # | 约束 | 为什么不可协商 | 可执行判定 |
|---|---|---|---|
| C1 | **已冻结的交付物不得改动** | 结论按哈希锚定；改一个字节旧结论即失效 | 变动文件的 sha256 ≠ 冻结清单 → REJECT |
| C2 | **权威口径只能有一处生效** | 两处并存则分歧时无从判断谁对 | 同一判据的生效声明数 > 1 → REJECT |
| C3 | **上游缺陷不得静默继承** | D1 已证明上游会错 | 引用版本出现在缺陷清单 → NEEDS_EVIDENCE |

C2 已有实现（`gates.js` 的 `gateSingleSource`），但**它检查的是交付包，
不检查本仓自身的引用一致性** —— 这正是 `tools.js` 与 `qa/index.js` 口径不一却没被拦住的漏洞。

## 五、内聚/低耦合：包边界重推

用户要求高内聚低耦合。回查当前 8 包，看依赖方向：

```
dsh-autoresearch        （引擎）        ← 被 ui / api 依赖
dsh-autoresearch-ui     （client 插件）
dsh-autoresearch-api    （凭据写入）
dsh-autoresearch-qa     （双路质检）← 跨包 join 到 gates/assets ← 耦合点
dsh-autoresearch-gates  （Python 门禁）
dsh-autoresearch-skills （技能目录）
dsh-autoresearch-remote （SSH）
dsh-ars-brand           （品牌）
```

**已发现的实际耦合违规**：
- `qa/index.js:83` 用 `join(projectRoot, 'packages', 'dsh-autoresearch-gates', 'assets', 'qa-0.3.4')`
  —— **qa 包硬编码了 gates 包的内部目录布局**。gates 一改目录结构，qa 静默失效。
- `gates/lib/tools.js:145,155` 用 `'skills-0.3.2/…'` 相对 assets
  —— **gates 包硬编码了 skills 包的资产**

这不是"包"，这是**共享目录的三个视图**。低耦合的正解：
把「上游来源」抽成**一个**明确的模块，其余包只通过它的 API 查询，不拼路径。

### 与 SOP 技能正文的交叉核对（发现一处口径差异）

`autoresearch-task-sop` 技能正文称：

> 来源附件的 `audit_task.py` 不支持 `--review`，`implementation_review.py` 才支持。

**实测该说法对应的是 0.3.2 那一份**：

| 文件 | `--review` | `--release-self-check` |
|---|---|---|
| `qa-0.3.4/audit_task.py` | ✅ | ✅ |
| `qa-0.3.4/implementation_review.py` | ✅ | ✅ |
| `skills-0.3.2/.../audit_task.py` | ✅ | ❌ |

0.3.4 里两份都支持全部参数。这不是技能写错了 —— 它描述的是它绑定的
那份快照（2026-10-05，对应 0.3.2）。**这恰好证明了本机制的必要性**：
"某能力属于某文件"这种事实会随版本变，写进正文就会过期，
而 `probeCapabilities()` 每次实测，永远不会。

据此把 `audit_task.py` 的 role 从 `release-evidence` 修正为 `audit`
（它是静态审计器，职责是收集而非产出结论）—— 职责标签按**实测职责**，
不按文件名的字面联想。

### 关键设计决定与理由

**决定 1：不做自动同步（L3）。**
理由：`docs/upstream-defects.md` 记录的 D1 是**真实的上游缺陷**。
自动同步会把它直接搬进来。改为「检测 + 人工/模型决策」。
`npm run upstream:accept` 是显式的接受动作 —— 有意的升级留下痕迹，
被动漂移则保持红色。

**决定 2：能力用实测而非声明。**
`UPSTREAM_SOURCES.capabilities` 是人写的，会过期。
`probeCapabilities()` 直接跑 `--help`，`upstream-baseline.mjs` 比对
「声明 vs 实测」，不一致即 DRIFTED。这使"声明腐化"本身可被发现。

**决定 3：不合并保存两份来源。**
`catalog.js` 的 rank 100/200 是**职责分级**，不是历史包袱。
自审质疑 1 断言"权威口径仍可解析且与发布门证据不是同一文件"。

### 失败模式（明确不做的事）

| 场景 | 行为 | 理由 |
|---|---|---|
| 上游新增版本 | 不自动跟进 | 避免引入未知缺陷；漂移检测会先报出来 |
| 基线缺失 | `UNKNOWN` + 退出码 2 | **不得**当成 IN_SYNC |
| 文件消失 | `UNKNOWN` | 同上 |
| 声明与实测不符 | `DRIFTED` | 防止声明腐化 |

### 判断标准（何时算"动态"做到了）

不是"代码里有了漂移检测"，而是：
> **上游发布 0.3.5 时，`npm run check` 变红，输出精确指出哪几个文件变了、
> 哪些能力声明失效，并且在 30 分钟内能由人或模型完成评估与接受。**

本轮完成了这条链路的**前半段**（发现与定位）。
后半段（评估与接受）目前是显式的人工命令 —— 这是刻意的成本取舍。
