## 二、逐项证据

### 1. QA15：两处表述方向相反（需平台确认哪一边成立）

教程两处：

> L16：`资源估算（QA15）` 完整单轮≤2 小时、≤8 张 H20/L20、≤64 核 CPU…
> L125：QA07/08 检查题面泄露；**QA15 检查有依据的资源估算**；QA18…；QA21…

SOP：

> `production-sop.md:802`：|QA15|静态 Skill **固定跳过平台资源上限**|
> `SKILL.md:100`：QA07/08 静态范围只是题面泄露，**QA15 静态跳过资源上限**

**两者可能可以调和，也可能真冲突** —— 有两种读法：

- 读法 A（冲突）：教程说 QA15 查资源，SOP 说 QA15 跳过资源 → 方向相反。
- 读法 B（可调和）：QA15 检查「估算**有没有依据**」，但不**强制上限**
  （即 SOP 的「跳过平台资源上限」指的是不因超限直接判失败，而教程的「检查有依据的
  资源估算」指的是要看证据）。这种读法下两边都成立。

**我无法判定哪种** —— 需要平台当前的 `autoresearch-task-qa` 才能确认 QA15 的实际行为，
而它不在随包资产里（随包只有 `qa-0.3.4` 的 9 个 python 脚本，无 QA 项定义）。

无论哪种读法，有一条是确定的：**SOP 该句的措辞会误导**。写「固定跳过资源上限」
会让专家以为资源数字不必核对，而教程 L16 明确要求「引用已有日志说明资源估算」。
**建议改成不含歧义的表述**，例如：「QA15 检查资源估算是否**有依据**；
是否**强制上限**由平台版本决定（见 V07）」。

实现侧现状（说明：**这是我本会话按教程加的，不构成平台行为证据**）：

```
合规（16c/1×H20/7200s）   → 全 PASS
CPU 题带 GPU（教程禁止）   → G15.4 UNKNOWN
超核（128c）             → G15.2 FAIL
非 H20/L20 卡型（A100）   → G15.4 UNKNOWN
超时（10800s）           → G15.1 UNKNOWN
```

它按「检查 + 强制上限」实现，属读法 A。**若平台实际是读法 B，这个门禁偏严**——
超限本应只提示不拦。这一条同样需要平台确认。

### 2. QA21 题包指纹：SOP 完全没提

教程 L18 / L892：

> `run_summary.json` 的 `task_binding` 记录 `hash_profile` 与 `task_content_sha256`；
> 范围固定为 `environment/`、`task.toml`、`tests/`、`instruction.md`。目录内全量递归…
> ```bash
> python3.11 <Skill目录>/scripts/task_fingerprint.py <harbor_task目录>
> ```

SOP 全文 grep：`task_binding` **0 次**、`hash_profile` **0 次**、`task_fingerprint` **0 次**。

SOP 有自己的哈希纪律（规则 18「运行绑定与交付字节交叉验证」、规则 21「取回历史产物必须哈希对账」），
但与 QA21 的**题包指纹**是两件事：前者是 SOP 自加的工程纪律，后者是**平台机检项**。
SOP 未载明后者，会导致专家交了包却没有 `task_binding` 两字段。

**注意**：工作台实现侧此前也没有这一项（我此前已登记为「待平台提供算法定义」，
因为 `task_fingerprint.py` 不在随包资产里）。两边都缺，不是 SOP 单独的问题。

### 3. 内场约束（`storage_mb` / 禁网 / 网络白名单）：SOP 完全没提

教程**四处**强调（L19、L131、L258、L985）：

> 不声明当前内场未支持的 `storage_mb`、禁网或网络白名单；**warning 后继续运行、
> 降级联网均不算约束生效**。若题目依赖这些条件，应先调整题面、环境和评分设计…

SOP 全文 grep：`storage_mb` **0 次**、`网络白名单` **0 次**。

这条的代价是实的：声明了不生效的约束，专家会以为自己限制了网络，实际没有，
于是**隔离设计从根上不成立**——而这类题会被平台按 H01–H06 打回。
SOP 讲了「怎么建隔离」，却没讲「哪些隔离声明在当前内场根本不生效」。

### 4. 模型组合：SOP 未载明「可调整」

教程 L5（开篇第一句）：

> 模型组合可调整，Skill 核对实际模型与独立运行条件，**不按示例型号判退**。

L655：

> **模型名称不作为固定验收条件，调整模型无需额外审批。**

SOP 规则 8：

> 三期快照指定 `Codex + GPT-5.6 Sol` 与 `Codex + Seed 2.1 Turbo`，同任务/Prompt/资源…

SOP 有「三期快照指定」这个前缀做限定，所以**不算写错**；但全文没有教程那句
「不按示例型号判退」，读者容易把示例型号当硬要求。

**实现侧已实测无此问题**：

```
换非示例型号（Claude-Opus-5 / Gemini-4-Ultra）→ G11:hours 全 PASS
```

门禁只读 `runtime`/`model` 作为标签，不比对具体名字。所以这是**SOP 文本层面的隐患**，
不是实现缺陷。

## 三、我自己的一处误判（更正）

我一度把 **Compose** 判为冲突，核查后**不成立**：

| | 说的是什么 | 层面 |
|---|---|---|
| 教程 L19/L111 | 「优先每个 sandbox **单容器**，不采用不受支持的 Compose **部署**」 | **任务方案**不得依赖多容器编排 |
| SOP L688 / `nop_preflight.py` | 「Harbor 走 compose 编排」→ 宿主须装 compose v2 插件 | **宿主环境**需具备该能力给 Harbor 内部用 |

两者不在同一层面，**不矛盾**。真机证据也支持 SOP：该题实际 NOP Trial
（Harbor 0.24.0，`harbor run -p … -a nop -e docker`）的日志里出现
`GPU selection follows the Compose device request` —— Harbor 的 docker 后端内部确实用 Compose。

所以 `nop_preflight.py` 把 compose v2 列为环境前提是对的，**不应按教程改掉**。
