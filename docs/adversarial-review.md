# 对抗性审查

> 立场：假设当前方案全部错误，逐条找证据推翻。
> 方法：从「这个工具要解决什么问题」出发，检验每个设计决定是否是最短路径。

---

## 零、问题定义

一个领域专家需要把一篇论文变成符合教程 V3 规格的 AutoResearch 任务包。
流程分四阶段，每阶段有门禁。门禁必须真跑、不可跳级。

核心需求：
1. 知道自己在哪个阶段、还缺什么 → **状态**
2. 门禁判定 → **判定**
3. 推进阶段 → **推进**
4. 留轨迹 → **留痕**

就是这四件事。其它一切——双路质检、远端执行、自定义 API、桌面 UI——
都是这四件事的附属品。

---

## 一、模式不是模式，是简报

**发现**：模式只注入文本，不限制行为。

`plan-mode` 的做法：注册 `agent/pre-step` 拦截器 + 用 `tools.restrict()`
**阻止**不该调用的工具。我的模式：0 次 `restrict` 调用。

后果：模型在模式下仍然可以调全部 29 个工具。它可以无视门禁直接调
`autoresearch_advance`（被 state.js 的逻辑拒绝），但它可以先调
`autoresearch_api_add`、`autoresearch_remote_submit` 或任何不相关工具。

**消融证据**：删掉整个模式，9 个工作流工具全部独立可用——
`state.js` 的 `advanceState()` 自己检查门禁，不依赖模式。
模式是**装饰**，不是**约束**。

**结论**：这不是模式。这是一封每次都发的提醒邮件。

---

## 二、29 个工具是工具箱，不是工作流

逐个审查后分类：

| 分类 | 数量 | 工具 | 判定 |
|---|---|---|---|
| 工作流动词 | 4 | init / gate / advance / trajectory | **保留** |
| 状态查询 | 3 | status / intake / audit | **删**（模式已注入） |
| 技能浏览 | 2 | skills / skill_read | **删**（harness 内置 skill 工具） |
| Python 门禁 | 2 | gate_env / gate_run | **合并为 1** |
| 双路质检 | 4 | qa_lanes / qa_pack / qa_dual / qa_verify | **合并为 2**（lanes 并入 dual；verify 并入 dual） |
| 远端执行 | 8 | target / probe / submit / probe_job / snapshot / restore / status / exec | **合并为 4**（target+probe、submit+probe_job、snapshot+restore、status+exec） |
| 自定义 API | 6 | options / add / list / verify / dual_lanes / probe | **合并为 3**（add 含 probe 和 verify；dual_lanes 含 list；删 options） |

**最少需要 14 个工具**。当前 29 个，多了 15 个——全是「查询」和「拆得太细的操作」。

根因：我不信任模式会工作，所以给模型准备了每个信息的查询入口。
模式如果真的注入了「现在该做什么」，查询工具就是冗余的。

---

## 三、7 个包，只需要 3 个

实际依赖图：

```
dsh-autoresearch（引擎）← dsh-autoresearch-ui ← dsh-autoresearch-api
dsh-autoresearch-skills（独立）
dsh-autoresearch-gates（独立）
dsh-autoresearch-qa（独立）
dsh-autoresearch-remote（独立）
```

4 个包（skills / gates / qa / remote）**零内部依赖**——它们不引用任何其它包。
它们之所以是独立包，是因为我按「能力」拆分，而不是按「耦合度」拆分。

按奥卡姆剃刀：**耦合度决定包边界**。
- 引擎 + gates + skills → 合为一个包（它们共享状态与阶段定义）
- qa → 独立（依赖 Python 工具，有独立的运行时）
- remote → 独立（依赖 SSH，有独立的运行时）
- api → 独立（依赖凭据文档写入，有独立的运行时）
- ui → 独立（client 插件，天然隔离）

5 个包。但仍比 7 个少。

更激进的做法：qa 和 remote 的核心逻辑不到 500 行，可以并入引擎。
api 的写入逻辑 ~200 行也可以。最终：**引擎 + ui = 2 个包**。

## 四、消融实验测错了东西

当前消融实验证明的是：

```
模式开 → 系统提示多了 326 字符、用户消息多了 1 条
模式关 → 没有这些
```

这证明模式**产出了差异**。但不证明模式**是必要的**。

真正的消融是：**移除模式后，模型在同一个任务上的产出是否退化？**

这需要 A/B 对比：同一个任务描述，有模式 vs 无模式，比较产出质量。
需要真实模型调用，成本高，但我没有做。

我做的 226 项测试的分类：

| 层 | 项数 | 测的是什么 | 能发现什么缺陷 |
|---|---|---|---|
| 纯函数 | 148 | 写代码的人验证自己写的代码 | 逻辑错误 |
| 机制产出 | 22 | 模式注入了什么 | 注入失效 |
| 一致性 | 22 | JS 与 Python 判定是否一致 | 上游缺陷（D1） |
| HTTP 可达 | 34 | 路由返回 200 | 路由挂了 |
| **模型行为** | **0** | **产出质量** | **模式是否有用** |

缺失的那一行是最重要的。我写了 226 项测试，但**不知道模式是否让模型做得更好**。

## 五、「会话恢复后模式保留」仍未真实验证

消融实验 F 组测试了：投影折叠命令事件后，新进程能恢复 `active: true`。

但这用的是**模拟事件序列**（我手动 append），不是真实 harness 的
持久化-重启-恢复循环。真实的 `sessionProjections.stateOf()` 在
进程重启后是否正确回放命令事件——我没有验证。

plan-mode 的同类测试在 harness 仓库内部有完整覆盖，但我的插件
不在那个仓库里，无法复用那些测试。

## 六、JS 门禁与 Python 门禁的「权威归属」是权宜之计

我给每道门禁标了 `authority: 'python' | 'js'`，声称 Python 是权威。
但 9 道门禁中 6 道的 JS 实现仍在运行，并且**逻辑不同**：

- JS `gateFeasibility` 支持 maximize 和 minimize，Python 只支持 minimize
- JS `gateDockerPathContract` 检查题面八章节，Python 不检查
- JS `gateTrajectory` 做 8 字段校验，Python `implementation_review.py` 做 QA16/18/21

这些不是「同一事实的两个实现」——它们检查**不同的东西**。
标 `authority: 'python'` 是在假装它们是同一件事。

诚实的设计：**每道门禁只有一个实现**。如果 JS 能检查某些 Python 不能检查的，
那就标 `authority: 'js'` 并说明原因，而不是假装 Python 是权威。

## 七、行动建议

### 立即做（收益明确，风险低）

1. **删 12 个查询工具** → 29 → 17。模式已注入这些信息。
2. **合并远端 8 → 4** → 按操作对分组。
3. **模式加 `restrict`**：激活时禁止调不相关的工具。
4. **修正权威归属**：按「谁真的检查了这个」标，不按「谁来自上游」标。

### 短期做（需要设计）

5. **7 → 5 个包**：合并 skills + gates 进引擎；qa / remote / api / ui 独立。
6. **补真实消融**：用真实模型跑同一任务，有模式 vs 无模式，量化差异。

### 不做（理由）

7. **不合并为 1 个包**：qa 依赖 Python 子进程、remote 依赖 SSH、api 依赖凭据写入。
   它们有不同的故障模式和生命周期，合并会让故障排查变难。
8. **不自定义会话事件**：已证明会导致日志不可读。命令事件方案是正确的。

## 八、值得保留的东西

审查不是全盘否定。以下设计经消融或实测验证是正确的：

1. **静态策略（章节）与动态指令（消息）分离** —— 消融实验发现共享值导致分叉后确立
2. **折叠命令事件而非自定义事件** —— CDP 测试发现日志不可读后确立
3. **上游缺陷 D1 的独立证明** —— 门禁一致性实验发现，暴力扫描证明
4. **与设置页共写 profile 用户层** —— 端到端测试发现覆盖后确立
5. **确定性 ZIP 打包器** —— 消融验证确定性一致
6. **U 方向校验** —— 对抗审查发现缺失后补上

这些不是「碰巧对了」——每一条都有具体的失效模式作为设计依据。
